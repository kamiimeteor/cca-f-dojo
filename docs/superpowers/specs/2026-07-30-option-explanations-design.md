# 错题逐项解析设计

日期：2026-07-30

## 背景

当前答错后的反馈会展示正确答案和题目总解析，但不能保证解释用户错选项以及其余选项。例如，用户把 `Grep` 选作生成子 agent 的工具后，只能看到 `Task` 为什么正确，仍不知道 `Grep` 的实际用途。

题库审计结果：

- 中文共 168 题，其中 129 题有完整的现有错项说明，39 题的错项说明为空，共缺 117 条错项说明。
- 英文共 168 题，其中 128 题有完整的现有错项说明，40 题的错项说明为空，共缺 120 条错项说明。
- 现有说明质量不统一，部分内容只有“无关”“同上”等简短判断，不能完整回答选项是什么、适用场景是什么、为何在本题中正确或错误。

## 目标

1. 保留现有答错提示、正确答案和题目总解析。
2. 仅在用户答错时，在原解析下方增加完整的逐项解析。
3. 对每个选项说明其含义或作用、典型适用场景，以及其在当前题目中为何正确或错误。
4. 同步覆盖全部 168 道题的中文和英文内容。
5. 支持单选题和多选题，并通过自动校验防止缺项或语言版本不一致。

## 非目标

- 答对时不展示逐项解析。
- 本次不增加“始终展示逐项解析”的用户设置；如后续收到明确反馈再迭代。
- 不修改题目顺序、随机抽题、续做进度或答题判定逻辑。
- 不改变题目总解析 `e` 的既有含义。

## 方案选择

题目视图统一生成 `optionExplanations` 数组：正确项读取现有总解析 `e`，错误项读取对应的错项说明 `w[index]`。本次补齐所有中英文 `w` 缺口，从而避免把同一批内容复制到第三套静态字段中。

理由：

- 渲染层获得与选项严格一一对应的数组，适合完整对照表。
- `e` 继续负责解释正确答案，`w` 继续负责解释每个错误选项，职责清晰且没有重复数据。
- 不改变 `w` 作为错项说明以及 `near` 校验依据的职责。
- 中英文继续按现有题目 ID 覆盖机制独立维护和校验。

## 数据模型

`qView()` 返回的题目对象增加运行时字段：

```js
optionExplanations: q.o.map((_, i) =>
  answerIndexes.has(i) ? q.e : q.w[i]
)
```

中文错项内容保存在 `assets/data/questions.js`，英文错项内容保存在 `assets/data/content.en.q1.js` 和 `assets/data/content.en.q2.js` 的同一题目 ID 下。

`qView()` 必须先合并对应语言的 `q`、`o`、`e`、`w`，再生成 `optionExplanations`，确保不会跨语言混用。当前系统只随机排列题目，不重新排列题目内部选项，因此数组按原始选项下标对齐即可；若以后增加选项乱序，必须让选项与逐项解析共享同一重排映射。

约束：

- 每道题的 `e` 必须为非空字符串，每个错误选项的 `w[index]` 必须为非空字符串。
- 生成后的数组长度必须与 `o` 的选项数量完全一致，且每一项非空。
- 顺序必须与题目选项顺序一致；选项标签由界面统一生成 A、B、C、D。
- 中文和英文都必须覆盖同一批 168 个题目 ID。

## 内容规则

逐项解析由左侧完整选项文本和右侧说明共同构成。对于工具、命令、模式等命名概念，右侧说明应尽量用一到两句话回答：

1. 该选项代表什么或能做什么。
2. 它通常用于什么场景。
3. 它为什么适合或不适合当前题目。

对于已经完整描述做法或后果的场景型选项，左侧文本本身已经回答“是什么”，右侧无需机械复述整句，但必须指出决定性的适用或排除理由。

内容遵循以下标准：

- 以官方能力边界和术语为准，不把站点自设做法表述成官方考试规则。
- 避免只有“无关”“同上”“不是答案”等缺少信息量的文本。
- 保持中英文语义一致，但不要求逐字直译。
- 正确项明确说明其与题干条件的对应关系。
- 干扰项同时解释其真实用途和本题不适用的关键原因，避免让用户误以为该工具或模式本身无用。

示例：

| 选项 | 逐项解析 |
| --- | --- |
| A · Bash | 用于执行 shell 命令，例如安装依赖或查看 Git 状态；它不能生成或委派子 agent，因此不符合题意。 |
| B · Task | 用于生成或委派子 agent；coordinator 要创建子 agent 时必须允许该工具，因此是正确答案。 |
| C · Read | 用于读取已知路径的文件内容；它不负责创建 agent，因此不符合题意。 |
| D · Grep | 用于按内容模式搜索文件和代码；它只能查找内容，不能生成子 agent，因此不符合题意。 |

## 展示与交互

用户提交错误答案后，反馈区按以下顺序展示：

1. “答错了——正确答案是……”标题。
2. 现有题目总解析 `e`。
3. “逐项解析”小标题。
4. A 方案的完整两列对照表：左列为选项标签和选项文本，右列为逐项解析。
5. 现有回笔记和下一题操作。

状态标记：

- 正确项使用绿色状态与“正确答案”标签。
- 用户错选项使用红色状态与“你的选择”标签。
- 其余选项使用中性色。
- 多选题允许多个绿色正确项，并标出所有用户错选项。
- 颜色之外同时使用文字标签，避免只靠颜色传递状态。

“逐项解析”“正确答案”“你的选择”等新增界面文案统一进入 `assets/data/i18n.js`，不在渲染函数内硬编码。

答对时保持当前反馈结构，不渲染逐项解析表。

## 响应式规则

- 桌面端使用两列表格，左列保持足够宽度以容纳选项文本。
- 小屏幕下每一行改为上下排列：先显示选项和状态标签，再显示解析正文。
- 不使用横向滚动作为主要方案。
- 长文本自然换行，代码和术语沿用站点现有排版规则。

## 兼容与回退

- 渲染前检查 `optionExplanations` 是否存在且长度正确。
- 开发阶段缺项由校验脚本直接报错，不能静默发布。
- 运行时若出现意外缺项，仍保留现有总解析和操作按钮，不让反馈区整体失效。
- 现有 `w` 字段先保留，避免影响 `near` 校验和其他答题模式；逐项解析表只读取 `optionExplanations`。

## 验证

自动校验至少覆盖：

- 中文 168 题均有 `optionExplanations`。
- 英文 168 题均有 `optionExplanations`。
- 每题说明数量与选项数量相等，且没有空字符串。
- 英文题目 ID 与中文题目 ID 完全对应。
- 单选错误、多选部分错误、答对三种状态的渲染行为符合规则。
- 缺失或异常数据不会阻断原反馈区。

校验沿用仓库现有 `scripts/test-*.js` 与 `scripts/check-i18n.js` 的轻量 Node 脚本方式，增加题库完整性和反馈区结构测试，并纳入项目现有的一键检查流程（如当前没有统一入口，则在 README 的开发检查说明中列出完整命令）。

浏览器验证至少覆盖：

- 中文和英文各抽查多个 Domain。
- `q012` 的 Bash、Task、Read、Grep 四项均完整可读。
- 桌面和移动宽度下表格无截断、无遮挡、无不必要横向滚动。
- 正确答案、用户选择和中性选项在颜色与文字标签上都能区分。
